# 步骤3：联网复核——标签来源与子代理批处理协议

预分类的系统性偏差来自 **Steam 商店标签泛滥**：`Simulation`/`Action` 这类宽泛标签几乎
处处都有，规则式分类会把纯动作游戏标成"模拟经营"、把卡牌构筑游戏标成"策略+战棋"。
复核的目的就是逐款用真实玩法修正。

## 标签/元数据来源（按成本从低到高）

| 来源 | 地址 | 给什么 | 建议 |
|---|---|---|---|
| M1 steamcmd.net API | `api.steamcmd.net/v1/info/<appid>` | store_tags + genres + developer/publisher + type | 全库底料，一次抓全（并发 ≤6，带重试，本地缓存可续传） |
| M1' Steam 官方 API | `store.steampowered.com/api/appdetails?appids=` | 同上更权威 | 有速率限制，适合抽查 |
| M2 SteamDB | `steamdb.info/app/<id>/info/` | 完整标签与元信息 | WebFetch 单点核实可疑款 |
| M2' Steam 商店页 | `store.steampowered.com/app/<id>/` | 描述+标签 | 地区限制时换 steamdb |
| M3 搜索引擎 | WebSearch | 真实玩法/评价/厂商事实 | 子代理逐款核实的主力 |

复核优先级：M1 全库打底 → 找出可疑款（C 数量异常多、与名称明显不符、待确认款）→
可疑款用 M2/M3 核实 → 用户要求全量时 M3 全库跑。

## M3 子代理批处理协议（核心）

把分类表切成批次（每批 20-30 款），每批派一个子代理。给子代理的提示词必须包含：

1. **协议引用**：搜索方法（每款至少一次 WebSearch；模糊时最多一次 WebFetch 商店页）、
   完整类目表（含每个代码一行释义）、判断准则（C 按真实玩法给 2-5 个；系列/厂商以
   搜到的事实为准；查不到就保留原值并标"否"）
2. **输入**：本批游戏清单 `appid | 名称 | installed | 当前分类 | 元数据摘要`
3. **输出**：无表头 CSV 每行 `appid,B_series,C_types,D_vendors,E_other,是否确定,判断依据`
   - **格式红线**（实战中子代理犯过的所有错）：英文逗号分隔（不是竖线）；7 列一个不能少
     （空值写空字符串，不许跳列）；依据里禁止英文逗号；不要在值里加 `B=`/`C=` 前缀
4. **幂等续跑**：若结果文件已存在，已有行（按 appid 区分）原样保留，只补缺失款
5. **防中断**：每核实完 5 款就把已完成行整体重写进结果文件（中断不丢进度）
6. **防上下文爆炸**：WebFetch 每款最多 1 次、失败立即放弃严禁重试同一 URL；
   游戏之间不输出总结性文字

### 子代理数量与批次大小（按用户情况增减）

两个旋钮：**并发数**（同时跑几个子代理）与**批次大小**（每批多少款）。按用户情况选档：

| 用户情况 | 批次大小 | 并发数 | 说明 |
|---|---|---|---|
| 限额未知（默认） | 25 | 先 2 探测 | 逐级上探（见下），被拒回落到最大稳定值 |
| 高配额 / 赶时间 | 30-50 | 3-6（探测上限内） | 吞吐优先；大批减少调度开销 |
| 低配额 / 控成本 | 30-50 | 1（串行） | 稳妥省心；批次放大减少总批次开销 |
| 预算极紧 | 不变 | 1 | 只复核高影响子集：C 类型 ≥6 个的、待确认的、已安装的 |
| 服务商不稳 / 频繁过载 | 15-20 | 1 | 小批快速落地，中断损失小 |
| 中断频发 | 15-20 | 1-2 | 配合幂等续跑，重派成本低 |

**并发探测协议**（不确定限额时执行）：
1. 同时派 2 个子代理，观察是否出现 "concurrency limit exceeded"
2. 稳定运行一个批次后加派第 3 个试探；被拒立即回落双路
3. 每提升一级都要等至少一个完整批次成功再继续升
4. 一旦某级被拒，该级即为上限，整轮固定在该值；不要反复试探浪费时间
5. 注意：子代理占满并发时，主会话自己的网络工具（WebSearch 等）也可能被限流——
   主会话兜底搜索要等有空槽时做

**重派与兜底**（与并发数无关，始终适用）：
- 子代理失败/被杀后直接重派同一批次（幂等续跑规则保证已有结果不丢）
- 同一批次连续 3+ 次在同一点失败 → 拆成两半重跑，并在提示词里加护栏
- 服务商过载（busy/quota）→ 等几分钟重试；个别顽固款由主会话亲自搜索兜底
- 完成一个批次立即补派下一批，保持并发槽位始终满载

## 结果文件的格式校验（merge 前必做）

实战发现的三类脏数据，写脚本统一修复：

```python
# 1) 竖线分隔行: 无英文逗号且含 '|' -> 按 '|' 拆分重组为逗号 CSV
# 2) 漏空列: 6 列且 row[1] 以 'C' 开头 -> 第2列前插入空 B 列
#            5 列且 row[1] 以 'B' 开头 -> 第4列后插入空 E 列与 '是'
# 3) 带前缀值: 字段以 'B='/'C='/'D='/'E=' 开头 -> 剥离前缀, '-' 转 ''
# 4) 依据混入英文逗号导致列数 >7 -> 把第 7 列之后合并回依据
# 5) 全部完成后: 行数应为 7, appid 必须存在于原表
```

## 汇总与回写

- `merge`：结果按 appid 与原表连接，**只覆盖 B/C/D/E 四列与"是否确定"**；
  A 状态不动（用户个人游玩状态）；工具类（E01）出现时清空 A 状态；
  未被复核覆盖的游戏保留原分类（支持部分完成）
- `apply`：回写前备份原表；回写后重建 state
- **汇报**：复核覆盖 X/Y、各列修正数、5-10 个前后对比样例 → **等用户确认**

## 成本参考（实测）

- 1000 款 ≈ 41 批 × 25 款；双路并发约 6-8 小时墙钟；单批 60-130 万 token
- 若预算有限：只复核"高影响"子集（C 类型 ≥6 个的、待确认的、用户常玩/已安装的）
